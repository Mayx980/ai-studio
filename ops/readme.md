# 构建与运行

在仓库根目录准备 Bun 1.3.14 及工作区依赖后，执行 `bun run build:server`。该脚本调用 `ops/buildStandalone.ts`，构建节点、工具、编辑器插件、Web、Server、MCP，并复制供应商和技能到根 `build/`。随后 `bun run start:server` 运行构建版，默认访问 `http://localhost:3000`。

容器入口为 `ops/Dockerfile` 和 `ops/compose.yaml`。在根目录执行 `docker compose -f ops/compose.yaml up --build`，构建上下文仍为仓库根；容器数据卷和端口沿用现有配置。容器构建、上线、签名、桌面和移动打包需要对应环境与独立操作，未执行时不声称通过。

平台准备、安装包、更新制品及发布命令的唯一详细说明见[源码手册](../docs/sourceDevelopment.md)与[更新服务](../services/updateServer/readme.md)。`.github/workflows/` 保留上游配置，在本 GitLab 项目不自动执行；本次不增加 GitLab CI 或生产部署。

## 独立账号运行方案候选（尚未实现）

Issue #7 的独立账号计划继续复用同一个 Bun/Express 容器及 appData 卷，不新增数据库服务；本轮不修改用户已有 APISIX，也不新增网关。测试环境仍可沿用宿主 31230 到容器 3000 的映射。不能在同一卷上启动多个可写应用副本。

候选实现将提供随聚合构建交付的本地 `createAdmin` 入口，由容器操作人员在受控终端输入初始用户名/密码，仅无账号时允许建立首个管理员。它不开放公网初始化接口，不提供固定演示密码，不把密码放进 Git、镜像、命令参数、日志或 Compose。计划确认并实现后再给出按实际产物验证过的完整命令，当前不存在可执行初始化入口。

升级前应停止应用并备份现有整个数据卷；旧共享目录和 Key 原位归首个管理员，新增用户目录与账号记录也保存在同一卷。备份包含凭据和密码哈希，按敏感资料保管，不能上传 Git。故障恢复须使用一致的整个数据卷和对应应用版本，不能只恢复项目文件或单独换回账号表；恢复到旧版会重新暴露其共享数据语义，因此不能把旧版回退视为安全的多用户访问。

独立 Server 默认要求真实登录，未完成管理员初始化时拒绝业务 API；健康检查可以检查公开静态首页的服务存活，不证明账号、保存或模型调用健康。当前 HTTP 内网地址仍可作测试，密码和 Cookie 的链路保密须由 HTTPS 提供；已有 APISIX 终止 HTTPS 时只接受明确可信的代理/公开地址配置，不信任任意转发头。精确配置与命令在实现后同步，不声称已完成目标机部署验收。
